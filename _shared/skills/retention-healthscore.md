# スキル：リテンションヘルススコア設計・定点観測

**使用するエージェント：** performance-analyzer（定点観測・主担当）／ insight-analyst（乖離の原因診断）／ content-strategist（モデル改修）
**入力：** リテンションモデル設計書（`retention-model.md`）・ロイヤリティ調査結果（`loyalty-research.md`）・CRM/購買データ・ES サーベイ
**出力：** KGIツリー・ヘルススコア定義書・定点観測ダッシュボード仕様・アラート基準・診断レポート・モデル改修提案

---

## このスキルの位置づけ

```
loyalty-research.md（測る）
    ↓
retention-model.md（設計する）
    ↓
retention-healthscore.md（設計したモデルが本当にKGIを動かしているかを定点観測する）★本スキル
    ↓
乖離があればモデルを改修 → retention-model.md へ戻る
```

**設計の中核となる問題意識：**
リテンションモデルは「描いて終わり」「一度検証して終わり」になりやすい。しかし、

- KGI（LTV・NRR等）は**遅行指標**であり、施策の成否が判明するのは半年〜数年後
- その頃には市場も顧客の事前期待も変化しており、**手遅れになってから気づく**
- 「顧客満足は上がったが売上が伸びない」という**連鎖の断絶**が起きても、どこで切れたか特定できない

→ したがって、**KGIに至る因果連鎖の各段階を先行指標として定点観測し、連鎖が切れた箇所を早期に特定する**仕組みが必要。これがリテンションヘルススコア。

**toB版との違い：** `customer-success.md` のヘルススコアは「個社アカウントの健全性」を測るもの。本スキルは「**リテンションモデルという設計そのものの健全性**」を測るもので、対象がアカウント単位ではなくモデル／セグメント単位である点が異なる。

---

## STEP 1：KGIツリーの分解（因果連鎖の可視化）

まず、リテンションモデルの設計要素がどのようにKGIへつながるかを4階層で分解する。

```
【第4階層】KGI（遅行指標・年次〜複数年）
    LTV／NRR／悪い売上比率／継続率
        ↑
【第3階層】ロイヤリティ指標（半遅行・四半期〜年次）
    ロイヤリティスコア（NPS/NRS）／ドライバー満足度／感情的な大満足の比率
        ↑
【第2階層】体験・プロセス指標（先行・月次）
    勝負プロセスの通過率と品質／作動スイッチの起動率／
    注力ポジティブ体験の発生頻度／削減対象ネガティブ体験の発生頻度
        ↑
【第1階層】前提条件指標（最先行・週次〜月次）
    事前期待の把握率／サービス品質6要素のオペレーション指標／
    ES（従業員満足）・定着率・生産性
```

### 分解のルール

- **各階層の指標は、上位階層と因果関係が検証済み**であること（`retention-model.md` PART2のチェーン検証で相関・有意差が確認されたもの）
- 検証されていない指標は「仮説段階」として明示し、観測しながら関係性を検証する
- **第1・第2階層を厚く設計する**。KGIだけを見ていても手遅れになるため、早期に動く指標を多く持つ

```markdown
## KGIツリー定義シート

| 階層 | 指標名 | 定義・算出式 | 観測頻度 | 上位階層との関係 | 検証状況 |
|-----|------|-----------|--------|------------|--------|
| 第4 | LTV | | 四半期 | ー | ー |
| 第3 | NRS | | 四半期 | LTVとの相関 r=  | 検証済/仮説 |
| 第2 | 勝負プロセス通過率 | | 月次 | NRSとの相関 r=  | 検証済/仮説 |
| 第1 | ES総合スコア | | 半期 | サービス品質との相関 r=  | 検証済/仮説 |
```

## STEP 2：ヘルススコアの構成指標と重み付け

5カテゴリを0〜10点で評価し、重み付けして100点満点に換算する。**リテンションモデルの設計思想（事前期待起点・勝負プロセス・感情的な大満足・CS/ES両立）がそのままカテゴリになる**よう設計する。

| カテゴリ | 測定する内容 | 重み | 主な指標例 |
|---------|----------|------|---------|
| **① 事前期待適合度** | 定めた事前期待の的に実際に応えられているか | 20% | 事前期待の把握率／的に据えた事前期待に対応するドライバー満足度／「余計なお世話」化していないか（該当ドライバーのネガティブ体験頻度） |
| **② 勝負プロセスの機能度** | 設計した勝負プロセスと作動スイッチが駆動しているか | 25% | 作動スイッチの起動率／勝負プロセスの通過率／勝負プロセスでのサービス品質評価／チャンスロス発生率 |
| **③ 感情的な大満足の創出** | 成果に直結する「感情的な大満足」が生まれているか | 25% | 感情的な大満足の比率（自由回答の分類）／注力ポジティブ体験の発生頻度／削減対象ネガティブ体験の残存頻度／体験琴線感度の高い体験の発生率 |
| **④ 経済ロイヤリティへの転化** | 心理ロイヤリティが実際に収益に転化しているか | 20% | 良い売上比率／悪い売上比率（逆転指標）／リピート率／紹介経由の新規獲得数 |
| **⑤ SPC健全性（ES側）** | 従業員側の連鎖が健全に回っているか | 10% | ES総合スコア／定着率／生産性／Aタイプ（顧客○×従業員○）の仕事の比率 |

```python
リテンションヘルススコア = (
    事前期待適合度スコア     × 0.20 +
    勝負プロセス機能度スコア  × 0.25 +
    感情的大満足創出スコア    × 0.25 +
    経済ロイヤリティ転化スコア × 0.20 +
    SPC健全性スコア          × 0.10
) × 10   # 100点満点に換算
```

**判定基準：**

| スコア | 判定 | 意味と対応 |
|-------|------|---------|
| 🟢 **80〜100** | Healthy | モデルが機能している。**勝ち筋の横展開・しくみ化（BUILD UP）へ進む** |
| 🟡 **60〜79** | Watch | 一部の連鎖が弱い。**低スコアカテゴリを特定して部分改修する** |
| 🟠 **40〜59** | Caution | 連鎖が複数箇所で切れている。**STEP6の原因診断を実施しモデルを見直す** |
| 🔴 **0〜39** | Critical | モデルの前提（事前期待の的）自体が誤っている可能性。**設計に立ち返る** |

### 重み付けのカスタマイズ指針

上記は標準配分。事業特性に応じて調整する。

- **リピート型（サブスク・EC）**：④経済ロイヤリティの重みを上げる（20%→25%）
- **一生に一度型（住宅・ウエディング等）**：②勝負プロセス（プロセスリピート）の重みを上げる（25%→30%）
- **労働集約型サービス業**：⑤SPC健全性の重みを上げる（10%→20%）
- ただし**③感情的な大満足の重みは下げない**。成果への分岐点そのものであるため

## STEP 3：定点観測サイクルの設計

指標の性質に応じて観測頻度を階層化する。**すべてを同じ頻度で見ようとすると運用が破綻する。**

| サイクル | 観測対象 | 目的 | 主な担当 |
|--------|--------|------|--------|
| **週次** | 第1階層の一部（オペレーション指標・ネガティブ体験の発生件数） | 異常の早期検知 | 現場／performance-analyzer |
| **月次** | 第2階層（勝負プロセス通過率・作動スイッチ起動率・注力体験の発生頻度） | モデルが駆動しているかの確認 | performance-analyzer |
| **四半期** | ヘルススコア全体＋第3階層（ロイヤリティ調査の簡易版） | **連鎖の健全性判定・モデル改修の要否判断** | performance-analyzer＋insight-analyst |
| **半期** | ES サーベイ（第1階層）／SPCチェーン検証 | CS・ES両輪の健全性確認 | performance-analyzer |
| **年次** | 第4階層（KGI）＋ロイヤリティ調査フルセット | KGI達成度の評価・翌年のモデル再設計 | chief-researcher含む全体 |

### 観測設計の原則

- **本格的なロイヤリティ調査（50問規模）は年1回**。四半期は主要ドライバーに絞った簡易版で代替する（回答負荷と精度のバランス）
- 第1・第2階層は**既存の業務データから自動取得できる設計にする**（都度アンケートを取ると運用が続かない）
- **観測の目的を「評価」ではなく「早期発見」に置く**。減点評価に使うと現場が数値を作りにいき、実態が見えなくなる

## STEP 4：アラート基準の設計

数値の絶対値だけでなく「**変化の兆し**」を捉える閾値を設ける。

```markdown
## アラート基準テンプレート

### レベル1：注意（週次で監視強化）
- いずれかのカテゴリスコアが前期比 -10%以上低下
- 削減対象ネガティブ体験の発生頻度が前月比 +20%以上
- 作動スイッチ起動率が目標値を2ヶ月連続で下回る

### レベル2：警告（月次で原因診断を実施）
- ヘルススコア総合が60点を下回る
- いずれかのカテゴリスコアが4.0（10点満点）を下回る
- 悪い売上比率が前四半期比 +5pt以上増加

### レベル3：重大（即座にSTEP6の原因診断とモデル改修判断）
- ヘルススコア総合が40点を下回る
- 第2階層は良好なのに第3階層が悪化（＝連鎖の断絶が発生している）
- ES総合スコアと顧客満足度が同時に低下（＝自己犠牲型の運用に陥っている疑い）
```

**特に注視すべきシグナル：「連鎖の断絶」**
第1・第2階層が良好なのに第3・第4階層が改善しない場合、**因果関係の仮説そのものが誤っている**可能性が高い。この場合は施策の実行強度ではなく、モデルの前提を疑う。

## STEP 6：乖離時の原因診断フロー

ヘルススコアが低下した、またはKGIが未達の場合、**どの階層で連鎖が切れているか**を上から順に切り分ける。

```
【診断1】KGIは未達だが、第3階層（ロイヤリティ指標）は良好か？
  YES → 心理ロイヤリティが経済ロイヤリティに転化していない
        → 確認：購買動線の障害／価格・在庫等のビジネス要因／
                「感情的な大満足」ではなく「論理的な大満足」を増やしていないか
        → 対応：④経済ロイヤリティ転化のカテゴリを深掘り

  NO  → 診断2へ

【診断2】第3階層は未達だが、第2階層（体験・プロセス指標）は良好か？
  YES → 体験は提供できているが心理ロイヤリティが動いていない
        → 確認：★事前期待の的が誤っている可能性が最も高い
                （応えている期待が「共通的な事前期待＝当たり前」になっていないか）
                注力した体験の体験琴線感度が実は低くないか
        → 対応：retention-model.md PART1に戻り、事前期待を再探索

  NO  → 診断3へ

【診断3】第2階層は未達だが、第1階層（前提条件指標）は良好か？
  YES → 設計したプロセスが現場で実行されていない
        → 確認：作動スイッチが起動していないか／勝負プロセスの設定自体が誤っているか
                現場がモデルにピンときていない（実行の壁）
        → 対応：retention-model.md PART3・PART4（実行の壁の突破）

  NO  → 診断4へ

【診断4】第1階層が未達
  → ES・オペレーション品質が土台から崩れている
    → 確認：自己犠牲型の運用になっていないか（Bタイプの仕事が増えていないか）
            失点撲滅型マネジメントに戻っていないか
    → 対応：retention-model.md PART2（SPC設計・ES側）から立て直す
```

### 診断時の必須確認事項

- [ ] 外部要因（季節性・競合の動き・市場環境の変化）を除外したか
- [ ] 観測データ自体に問題はないか（回答率の急落・集計ロジックの変更）
- [ ] セグメント別に見ると特定セグメントのみ悪化していないか（全体平均が実態を隠していないか）
- [ ] **モデルの前提だった事前期待が、市場変化で陳腐化していないか**

## STEP 7：モデル改善サイクルへの接続

診断結果に応じて、`retention-model.md` のどのPARTに戻るかを決める。

| 診断結果 | 戻り先 | 改修の粒度 |
|--------|-------|---------|
| 経済転化の断絶（診断1） | PART3（プロセス）＋ビジネス要因の改善 | 部分改修 |
| 事前期待の誤り（診断2） | **PART1（事前期待探索）** | **モデルの再設計** |
| 実行されていない（診断3） | PART3（勝負プロセス・作動スイッチ）＋PART4（実行の壁） | 部分改修＋推進強化 |
| 土台の崩壊（診断4） | PART2（SPC・ES側） | 土台の立て直し |

### スパイラルアップの運用

改修は「失敗」ではなく「**実験室で得た学び**」として扱う（`retention-model.md` PART4「確信に変える力」）。

- ヘルススコアの推移そのものが、モデルの仮説検証ログになる
- 改修のたびに「何を変えたら、どの指標がどう動いたか」を記録し、knowledge-curatorへ蓄積する
- **改修履歴とスコア推移をセットで残すことが、組織の再現性を高める最大の資産**になる
