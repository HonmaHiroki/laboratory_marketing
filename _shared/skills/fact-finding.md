# スキル：ファクトファインディング（仮説確認・提案への橋渡し）

**使用するエージェント：** abm-strategist（仮説設計）／ sales-enablement-executor（ヒアリングシート生成）
**入力：** account-intelligence-analystの「3C+2C×マクロ環境」分析（勝ち筋仮説）・stakeholder-mapperのステークホルダー情報
**出力：** 仮説ヒアリングシート（軽量・1〜2ページ）・ファクトファインディング議事メモ・オーダーコントロールへの申し送り事項

---

## このスキルの位置づけ

`_shared/skills/consulting-sales-process.md`の7工程のうち、**③ファクトファインディング**（合意×4・共感×1）を
実行するための専用スキル。**④プレゼンテーション段階で使う`proposal-writing.md`とは目的も資料の重さも異なる。**

```
③ファクトファインディング（本スキル）→ ④オーダーコントロール → ⑤企画作成 → ⑥プレゼンテーション（proposal-writing.md）
   軽量な仮説確認                    方向性の合意          企画書ドラフト    重厚な提案書・ROI試算書
```

| | ③ファクトファインディング（本スキル） | ⑥プレゼンテーション（`proposal-writing.md`） |
|--|--------------------------------|------------------------------------|
| **目的** | 事業理解・現状・理想・問題について認識のズレがないか**合意**を取り、課題設定に**共感**してもらう | 具体的な解決策・ROI・投資対効果を提示し、**意思決定**してもらう |
| **資料の重さ** | 1〜2ページの仮説ヒアリングシート。会話の補助線であり主役ではない | 提案書8ステップ構成・ROI試算書・PPTXスライド実装（19スライド） |
| **ROI試算** | **不要**。まだ解決策を提示する段階ではない | 必須（STEP3） |
| **失敗パターン** | 重厚な提案書をこの段階で作り込んでしまい、方向性がズレていた場合に手戻りが発生する | 逆に、ここで仮説確認を飛ばして企画書を作り込むと同じ手戻りが起きる |

**このスキルの核心：「白紙でヒアリングに行かない」。** 何も仮説を持たずに「御社の課題は何ですか？」と聞くのではなく、
`account-intelligence-analyst`の分析から導いた仮説を**先に提示し、合意・修正してもらう**形で進める。
これにより、顧客は「話を聞いてもらえた」ではなく「よく理解してくれている」という信頼を持つ（`consulting-sales-process.md`の
「わかってるね感」に相当）。

---

## STEP 1：仮説の事前設計（ヒアリング前に必ず準備する）

`account-intelligence-analyst`の「3C+2C×マクロ環境」分析（勝ち筋仮説）と、`_shared/skills/proposal-writing.md`
STEP0の「課題発見の公式」（7つのファクト）のフレームを使い、**ヒアリングに行く前に**仮の答えを埋めておく。

```markdown
## 仮説事前設計シート（ヒアリング前に作成）

### i. 事業理解の仮説
- 想定するビジネスモデル：
- 想定する主要な収益源：
- （account-intelligence-analystの3C+2C分析より）想定される「顧客の顧客」「顧客の競合」：

### ii〜iv. 現状・理想・問題の仮説
- 現状（－）の仮説：（例：受注数が目標に対して月10件不足している）
- 理想（＝）の仮説：（例：事業目標達成に必要な受注数）
- 問題（現状と理想のギャップ）の仮説：

### v〜vii. 原因・示唆・課題の仮説（提示するというより「一緒に深掘りする」余白として用意）
- 想定される原因の仮説（複数用意し、ヒアリングで検証する）：
- 課題（やるべきこと）の仮説：

### 確認したいステークホルダー
- 本日の対話相手：（役職・stakeholder-mapperのDiSCスタイル）
- 決裁者・推進者との関係性で確認したいこと：
```

**原則：** 事業理解・現状・問題の仮説は「確信度70%程度」で用意する。100%の確信を持って断定的に提示すると、
外れていた場合に「分かっていない」という印象を与えてしまう。**「〜という理解でよろしいでしょうか」という
確認の姿勢**を保つ。

---

## STEP 2：仮説ヒアリングシートの構成（軽量・1〜2ページ）

提案書（`proposal-writing.md`）のような多ページのスライドは作らない。**A4 1〜2枚、または画面共有1〜2スライド程度**の
シンプルな構成にする。

```
① 本日のゴール（このヒアリングで確認したいことを冒頭で明示）
② 事業理解の確認（仮説を提示し、認識のズレを確認）
③ 現状・理想の確認（数値化された仮説を提示し、実数を教えてもらう）
④ 問題の仮説提示（「〜という問題があるのではと見ていますが、いかがでしょうか」）
⑤ 原因の深掘り（whyを繰り返し、顧客自身の言葉で語ってもらう）
⑥ 課題への共感確認（「この課題に取り組む必要があるとお感じになりますか」）
⑦ 次のステップの共有（この後どう進めるかを明示。オーダーコントロールへの橋渡し）
```

**含めないもの：** 解決策の詳細・ROI試算・価格・導入スケジュール。これらは①〜⑦で合意・共感が取れた**後**の
工程（④オーダーコントロール以降）で扱う。ファクトファインディングの段階で解決策を語り始めると、
顧客側の「まだ課題を理解されていないのに解決策を押し付けられている」という警戒を招きやすい。

---

## STEP 3：4つの合意と1つの共感を得るための質問設計

`consulting-sales-process.md`が定義する「合意×4・共感×1」を、具体的な問いかけに変換する。

```markdown
## 合意①：事業理解への合意
「私どもでは御社の事業を〇〇と理解しておりますが、認識に相違はございませんか」
→ 相違があれば素直に訂正してもらい、シートを更新する

## 合意②：現状への合意
「現状、〇〇という状況とお見受けしていますが、実際の数字感としてはいかがでしょうか」
→ 具体的な数値を引き出す（概算でも可）

## 合意③：理想への合意
「理想としては〇〇を目指されているという理解ですが、これで合っていますか」
→ 期限・目標値等、可能な範囲で具体化してもらう

## 合意④：問題への合意
「現状と理想の間には〇〇というギャップがあるように見えていますが、この認識で合っていますか」
→ ここで初めて「問題」の言語化について合意を得る

## 共感：課題への共感
「原因を辿ると〇〇にあるのではと考えていますが、そうだとすると、これは今取り組むべき課題だとお感じになりますか」
→ 「はい、その通りです」という共感の言葉を引き出せれば、④オーダーコントロールへ進める準備が整う
```

**進め方の原則：** ①→②→③→④→共感の順で、**前の合意が取れてから次に進む**。合意が取れないまま先に進むと、
土台が崩れたまま話を続けることになり、後工程（プレゼンテーション）で「そもそも認識が違った」という
致命的な手戻りにつながる。

---

## STEP 4：ファクトファインディング議事メモの作成（ヒアリング後）

```markdown
## ファクトファインディング議事メモ：[アカウント名]

- 実施日：
- 対話相手：（役職・氏名）
- 使用した仮説ヒアリングシートのバージョン：

### 合意状況
| 項目 | 事前仮説 | ヒアリング結果 | 合意状況 |
|-----|--------|------------|--------|
| 事業理解 | | | ✅合意 / △一部修正 / ❌大幅な相違 |
| 現状 | | | ✅合意 / △一部修正 / ❌大幅な相違 |
| 理想 | | | ✅合意 / △一部修正 / ❌大幅な相違 |
| 問題 | | | ✅合意 / △一部修正 / ❌大幅な相違 |

### 課題への共感度
- 共感の有無：あり / 中立 / なし
- 顧客自身の言葉で語られた内容（そのまま記録する。要約しすぎない）：

### 原因・示唆の深掘り結果
- 語られた原因：
- こちらから提示して響いた示唆：
- まだ検証しきれていない仮説：

### 次のステップ（④オーダーコントロールへの申し送り）
- 提案の方向性（何を軸に企画するか）：
- 巻き込むべき追加ステークホルダー：
- オーダーコントロールで確認すべき要件定義項目（`proposal-writing.md`STEP2「要件定義すり合わせシート」を参照）：
```

**この議事メモが、`proposal-writing.md`STEP0の「7つのファクト」の実際の中身になる。** ファクトファインディングで
埋めた「現状・理想・問題・原因・示唆・課題」を、そのままプレゼンテーション段階の提案書に引き継ぐ。

---

## STEP 5：オーダーコントロールへの橋渡し

合意④・共感が取れたら、**次のステップを顧客と共有してから会話を終える**。ここで提案の詳細を語り始めない。

```markdown
## 次回に向けた共有事項（口頭またはメールで）

「本日確認させていただいた内容をもとに、〇〇様の課題解決に向けた具体的な提案の方向性を整理いたします。
 次回、その方向性について簡単にすり合わせのお時間をいただけますと幸いです」

→ これが consulting-sales-process.md の④オーダーコントロール（提案の方向性そのものへの合意）の入口になる
```

**共感が得られなかった場合：** 課題設定に共感が得られない場合は、無理に④オーダーコントロールへ進まない。
STEP1の仮説設計に戻り、原因・示唆の仮説を再検討してから再度ヒアリングの機会を設ける。

## 品質チェックリスト

- [ ] ヒアリング前に「仮説の事前設計」を行い、白紙の状態でヒアリングに臨んでいないか
- [ ] 仮説ヒアリングシートが1〜2ページの軽量な構成に収まっているか（多ページのスライドになっていないか）
- [ ] 解決策・ROI試算・価格・スケジュールに、この段階で踏み込んでいないか
- [ ] 4つの合意（事業理解・現状・理想・問題）を順番に、前の合意を得てから次に進めたか
- [ ] 課題設定への共感を、顧客自身の言葉で確認できたか
- [ ] 議事メモが`proposal-writing.md`STEP0の「7つのファクト」にそのまま転記できる形で整理されているか
- [ ] 共感が得られなかった場合に、無理にオーダーコントロールへ進まず仮説を再設計したか
